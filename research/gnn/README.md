# Stage 3.5: duration GNN

Predicts **log(actual ÷ planned duration)** per activity from the schedule network. The aim is to correct PMI's rule-based task durations.

```powershell
python -m pip install -r research\gnn\requirements.txt        # PyTorch, PyTorch Geometric, scikit-learn, openpyxl
python research\gnn\dslib.py                                   # build the dataset from data\raw\ghent (cached)
python research\gnn\train.py --source synthetic                # check that the graph layers can learn
python research\gnn\train.py --source dslib                    # real projects, every G/G project included
python research\gnn\train.py --source dslib_filtered           # sensitivity variant (rules in dslib.FILTER_RULES)
python research\gnn\evaluate_overrun.py                      # overrun AUC from saved predictions (no retraining)
python -m unittest tests.test_gnn
```

Outputs go to `models/gnn_<source>/`: `report.md`, `metrics.json`, `oof_predictions.csv` and `overrun_auc.json` are versioned. `model.pt` (the model refit on all projects) is regenerated by `train.py` and is git-ignored: no checkpoint is fit for use (see below).

## Design

| Part | Choice |
|---|---|
| Graph | Activities are nodes; precedence links are edges, with predecessor and successor directions kept as separate relations |
| Node features | Only what is known at planning time: log planned days, share of the project, CPM early start and float, critical flag, in/out degree, depth, project size, and trade category (one-hot) |
| Trade category | From activity names, using English, Dutch and French keywords. PMI tasks map directly from their work package, so a model trained on DSLIB can be applied to PMI-generated schedules |
| Model | `DurationGNN`: 3 GraphSAGE layers per direction with a residual connection. `NodeMLP` has identical inputs and no message passing, as the control |
| Evaluation | 5-fold cross-validation over **groups of related projects** (the Stage 2 audit's conservative grouping). 15% of the training groups are held out for early stopping. Compared against plan, global median, per-category median and MLP; paired bootstrap over projects |

## Results (out-of-fold predictions)

| Data | Projects (independent groups) | Activities | Plan MAE | MLP MAE | GNN MAE | MLP overrun AUC, fold range | GNN overrun AUC, fold range |
|---|---|---|---|---|---|---|---|
| Synthetic (planted neighbour effect) | 120 (120) | 2,510 | 4.08 d | 1.63 d | **0.80 d** | 0.87–0.92 | 0.97–0.98 |
| DSLIB, all G/G | 53 (17) | 2,712 | **2.69 d** | 3.09 d | 3.01 d | 0.43–0.61 | 0.40–0.57 |
| DSLIB, filtered | 40 (15) | 2,051 | **3.37 d** | 3.62 d | 3.56 d | 0.35–0.66 | 0.42–0.62 |

MAE is the mean absolute error per activity, from out-of-fold predictions (`metrics.json`). The overrun AUC (`overrun_auc.json`, from `evaluate_overrun.py`) measures how well a method ranks activities by the risk that `actual > 1.05 × planned`; 0.5 is chance. Overruns are 17% of real activities (20% filtered) and 89% of synthetic ones.

### Interpretation

1. **The code works.** On synthetic data whose labels depend on neighbouring activities, the GNN halves the MLP error, and the difference is significant.
2. **On the real data, no model beats "actual = planned".** 71% of DSLIB activities finished exactly on plan, so under absolute error the best estimate is no deviation. The GNN has a slightly lower per-activity MAE than the MLP. That is not a consistent advantage: on the filtered data its mean error per *project* is worse (6.80 vs 6.38 days), and no significance test between the two was run on real data. Both are worse than the plan.
3. **No transferable signal for *which* activities overrun.** Per-fold AUCs scatter around chance (0.35–0.66 across MLP and GNN, pooled 0.38–0.52), and no method is above 0.5 in every fold. Planning-time network features and trade category don't predict activity-level deviation in new projects.
4. **Limiting factors:**
   - Only **15–17 independent project groups**.
   - Labels dominated by exactly-on-plan values. All 11 "Residential House Finishing Works" projects are 100% on plan, which suggests their tracking mirrors the baseline.
   - Activity names are inconsistent: 22% match no trade.
   - There is no BIM, crew, weather or change-order information.

**Do not apply this model to PMI schedules as a duration correction.** It doesn't beat the plan. Report it as a negative result with a working, tested pipeline. That is a legitimate Stage 3.5 finding.

## Data that would be needed

The unit that matters is the **project**: activities within one project are correlated. A BIM-linked version of this model would need, for each project:

1. The construction-issue **IFC model**.
2. The **baseline programme**: activities, predecessors with type and lag, planned durations.
3. The **as-built record**: actual start and finish per activity. These are the labels.
4. A **link between activities and model elements**: a 4D model, or activities coded by level, zone and trade.
5. **Context**: calendar, crew sizes, building type, change orders with dates, delay causes.

About 20–30 projects of a similar type are needed for a proof of concept, and 50–100 or more for a credible result.

## Simplifications

- FS, SS, FF and SF relations are all kept as edges, but the CPM features treat them as finish-to-start; lags are ignored.
- 8 hours per day is assumed. The label is a ratio of two durations in the same unit, so this assumption largely cancels out.
- Only completed activities in the last tracking period are labelled (Remaining Duration = 0).
